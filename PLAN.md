# Plan: spec → builder → review → PR flow

Oct 21, 2026 · @Arthur Toledo Neto · Portuguese version: [`PLAN.pt-BR.md`](PLAN.pt-BR.md)

## Overview and decisions

The flow is a Claude Code plugin with two commands (`/flow-init` and `/ship`) and seven subagents. `/ship` orchestrates everything from the main session.

| Decision                   | Choice                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------- |
| Where orchestration runs   | Main session, inside the `/ship` skill                                                          |
| Spec writer                | Opus 5.5, in planning mode                                                                      |
| Builder                    | Opus 5.5 by default; Fable when you pick it at triage                                           |
| Reviewers                  | Sonnet 5.5, read-only, in parallel                                                              |
| Which reviewers run        | Decided by the files changed in the slice                                                       |
| Loop trigger               | Only `blocker` or `major` findings; at most 2 rounds per slice                                  |
| Rounds exhausted           | The PR opens as a draft, with the pending findings                                              |
| Large feature              | Becomes N medium stacked PRs targeting an integration branch; only that branch opens a PR to the base |
| Findings                   | PR comments, via `gh`                                                                           |
| Environment                | Local Claude Code CLI + authenticated `gh` only                                                 |
| Per-project configuration  | Generated by `/flow-init` in `.claude/flow.json`                                                |
| Language                   | English or Brazilian Portuguese, chosen in `/flow-init` and stored in `flow.json.language`      |

Why orchestration lives in the skill and not in an agent: the human gates (triage and spec approval) need to talk to you, and that works reliably in the main session. Nested subagents exist since v2.1.172 (up to 5 levels), but some agent types reportedly don't get the delegation tool. The plan doesn't depend on that.

## Plugin structure

The plugin lives in its own repository and is installed in every project. Each project keeps only its own configuration and run artifacts.

```
flow-plugin/
  .claude-plugin/plugin.json
  .claude-plugin/marketplace.json  # the repo is also its own marketplace
  .mcp.json                       # Playwright MCP
  skills/
    flow-init/SKILL.md            # maps the project and writes .claude/flow.json
    ship/SKILL.md                 # orchestrates the whole flow
    ship/reference/
      review-schema.json          # reviewer output contract
      reviewer-routing.md         # which globs trigger which reviewers
      pr-body.md                  # PR description templates
      state.md  github.md  browser.md
  agents/
    spec-writer.md  builder.md
    security-reviewer.md  ux-reviewer.md  ui-reviewer.md  code-reviewer.md
    browser-tester.md
  checklists/
    security.md  ux.md  ui.md  code.md
  scripts/                        # deterministic logic, dependency-free Node

# in each project
.claude/flow.json                 # generated by /flow-init
.claude/checklists/*.md           # optional: overrides or extends the plugin's
.claude/flow-runs/<slug>/         # spec, findings per round, state (gitignored)
```

Before implementing, Claude Code must check the current documentation for the `plugin.json` format and how plugin skills and agents are discovered. (Done in phase 1: see `docs/phase-1-verification.md`.)

## Commands

`/flow-init` runs once per project. `/ship` runs for each change and picks up where it left off if interrupted. Inside Claude Code, the plugin namespaces them as `/flow:flow-init` and `/flow:ship`.

### /flow-init

1. Asks which language to use (English or Português) and writes it to `flow.json.language`.
2. Reads the remote branches (`main`, `dev`, `develop`, `release/*`) and the repository's default branch.
3. Reads the quality commands from `package.json`, `Makefile` or equivalents: lint, typecheck, tests, build.
4. Detects the stack and the frontend, backend and infra folders, for reviewer routing.
5. Confirms with you, through multiple-choice questions, the base branch for each change type, the branch prefix, and whether hotfixes need a back-merge.
6. Writes `.claude/flow.json` and adds `.claude/flow-runs/` to `.gitignore`.

```json
{
  "language": "en",
  "branches": {
    "feature": "dev",
    "bugfix": "dev",
    "refactor": "dev",
    "chore": "dev",
    "hotfix": "main"
  },
  "hotfixBackMerge": "dev",
  "branchPrefix": {
    "feature": "feat/",
    "bugfix": "fix/",
    "hotfix": "hotfix/",
    "refactor": "refactor/",
    "chore": "chore/"
  },
  "commands": {
    "lint": "npm run lint",
    "typecheck": "npm run typecheck",
    "test": "npm test",
    "build": "npm run build"
  },
  "routing": {
    "ui": ["src/**/*.tsx", "**/*.css", "**/*.scss"],
    "ux": ["src/app/**", "src/pages/**", "src/screens/**"],
    "security": [
      "**/auth/**",
      "**/*.controller.ts",
      "**/migrations/**",
      "Dockerfile",
      "**/*.tf",
      "package.json"
    ]
  },
  "maxReviewRounds": 2,
  "maxGateAttempts": 3
}
```

If the project only has `main`, `/flow-init` points every change type to `main`.

### /ship

1. Pre-checks: `flow.json` exists (otherwise it suggests `/flow-init`), the working tree is clean, and `gh auth status` is ok.
2. Triage with multiple-choice questions:
   1. Change type: feature, bugfix, hotfix, refactor or chore.
   2. Builder model: Opus 5.5 (default) or Fable.
   3. The base branch suggested by `flow.json`, for you to confirm.
3. The spec writer produces `.claude/flow-runs/<slug>/spec.md`, already sliced. Bugfix and hotfix get a single slice.
4. Human gate: you approve or ask for changes; changes go back to the spec writer.
5. Branches:
   - With more than one slice, it creates the integration branch `feat/<slug>` from the base.
   - Slice 01 branches off the integration branch, and each later slice branches off the previous one (stacked), named like `feat/<slug>-01-<summary>`.
   - With a single slice, the branch comes straight from the base.
6. For each slice:
   1. The builder implements with TDD and conventional commits.
   2. The quality gate runs the commands from `flow.json`. On failure, the same builder fixes it, up to 3 attempts; then it stops and calls you.
   3. Routing: `git diff --name-only` against the slice base, matched against the globs. The code reviewer always runs.
   4. The selected reviewers run in parallel, in a single message with several agent calls.
   5. The skill validates and consolidates the JSON and removes duplicate findings.
   6. If there was a `blocker` or `major` and the round is below 2, it resumes the same builder with the findings and goes back to step 2.
   7. Push, then `gh pr create` to the integration branch (or the base) — as a draft if a blocker remains — and publish the findings as comments.
7. Finalize with `/ship --finalize <slug>`: once the slices are in the integration branch, it opens the integration → base PR with a summary of every slice.
8. State lives in `.claude/flow-runs/<slug>/state.json`, so `/ship --resume <slug>` can continue after an interruption.

## Language

Everything the flow produces for people follows `flow.json.language` (`en` or `pt-BR`):
- the conversation;
- the spec;
- commit descriptions;
- PR titles and bodies;
- review findings and comments.

Code, identifiers and file names stay as they are in the codebase. Conventional commit types and scopes stay as keywords.

The orchestrator passes `Language: <lang>` to every agent, and the scripts take `--lang` for the text they generate.

## Agents

There are seven agents (the seventh, `browser-tester`, is described in the next section), each in a file under `agents/`, with a fixed model and fixed tools in the frontmatter. Only the builder writes code.

| Agent               | Model                     | Tools                                         | Input                            | Output                  |
| ------------------- | ------------------------- | --------------------------------------------- | -------------------------------- | ----------------------- |
| `spec-writer`       | Opus                      | Read, Grep, Glob, Write (only in `flow-runs/`) | Request, change type, `CLAUDE.md` | Sliced `spec.md`        |
| `builder`           | Opus; Fable by override   | Read, Edit, Write, Bash, Grep, Glob           | Spec slice or findings           | Code, tests, commits    |
| `security-reviewer` | Sonnet                    | Read, Grep, Glob, read-only Bash              | Diff, slice, checklist           | Review JSON             |
| `ux-reviewer`       | Sonnet                    | Read, Grep, Glob                              | Diff, slice, checklist           | Review JSON             |
| `ui-reviewer`       | Sonnet                    | Read, Grep, Glob                              | Diff, slice, checklist           | Review JSON             |
| `code-reviewer`     | Sonnet                    | Read, Grep, Glob, read-only Bash              | Diff, slice, checklist           | Review JSON             |

### Rules for each agent

- **`spec-writer`**:
  - Every slice has a goal, likely files, testable acceptance criteria, the tests to write, and its dependencies on other slices.
  - A slice targets up to about 400 lines of diff.
  - It lists open questions instead of inventing requirements.
- **`builder`**:
  - It writes the failing test first, then the code.
  - It follows Clean/Hexagonal architecture when the project already uses it.
  - It doesn't touch files outside the slice scope without justifying it.
  - When resumed, it handles each finding and replies `fixed` or `disputed + reason`.
- **Reviewers**:
  - They only read.
  - They review only the slice diff and the context they need, never the whole repository.
  - Every finding points to a file and line, with evidence and a suggested fix.
  - With no concrete finding, they return an empty list.
- `code-reviewer` always runs; the other three depend on routing.

The builder is resumed with the same context between rounds (`SendMessage` with the agent id) instead of starting a new agent. The builder's model comes from the `model` parameter of the call, which overrides the frontmatter.

## Real browser testing

Every slice that touches the web frontend goes through a seventh agent, `browser-tester`. It starts the app locally and uses Playwright MCP to run the acceptance criteria in a real browser, in the same round as the reviewers.

### Two layers

1. **Versioned E2E tests**: the builder writes Playwright tests (`e2e/*.spec.ts`) for every acceptance criterion of the slice. They join the quality gate and stay in the repository, running from then on.
2. **Exploratory testing**: the `browser-tester` browses like a user. It clicks, fills in forms, tries the happy path, errors and edge cases, and checks what the written tests may have missed.

### What the browser-tester checks

- Every acceptance criterion works end to end on screen.
- The console has no errors, and there are no failed network requests (unexpected 4xx or 5xx).
- Screens at 3 widths (320, 768 and 1280 px), with a screenshot of each.
- Keyboard-only navigation through the new flows.
- An accessibility scan with axe-core injected into the page.
- Core Web Vitals measured with Lighthouse on the local production build, when the project has one.

An acceptance criterion that fails in the browser is always a `blocker`. Screenshots go to `.claude/flow-runs/<slug>/slice-NN/round-N/screens/`, and the summary goes into the PR comment.

### Configuration in flow.json

```json
"browser": {
  "devCommand": "npm run dev",
  "url": "http://localhost:3000",
  "readyPath": "/health",
  "seedCommand": "npm run db:seed:test",
  "testUser": { "fromEnv": ["E2E_USER", "E2E_PASSWORD"] },
  "viewports": [320, 768, 1280]
}
```

- `/flow-init` detects the dev command and port, and asks how to create test data and a test user.
- Credentials come from environment variables or the project seed, never from real accounts.
- The plugin declares Playwright MCP in its own `.mcp.json`, so users don't need to set anything up.
- `/ship` starts the server before the round, waits for `readyPath` to respond, and stops it at the end.
- React Native is out of scope for now: Playwright only covers the web. Native mobile could come later with Maestro.

## Review contract and loop rules

Every reviewer returns exactly this JSON. If the output doesn't match the format, the skill rejects it and asks again, once.

```json
{
  "reviewer": "security",
  "round": 1,
  "summary": "One sentence on the state of the slice",
  "findings": [
    {
      "id": "SEC-001",
      "severity": "blocker",
      "category": "A01 Broken Access Control",
      "file": "src/orders/orders.controller.ts",
      "line": 42,
      "evidence": "GET /orders/:id does not check the order owner",
      "fix": "Filter by the token userId in the repository",
      "checklistRef": "security.md#A01"
    }
  ]
}
```

| Severity  | Meaning                                                                                                   | Back to the builder?         |
| --------- | --------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `blocker` | Security flaw, data loss, functional breakage, unmet acceptance criterion                                 | Yes                          |
| `major`   | Likely bug, missing test on a critical path, measurable accessibility or performance regression           | Yes                          |
| `minor`   | Clear but non-urgent improvement                                                                          | No; becomes a comment        |
| `nit`     | Style and preference                                                                                      | No; becomes a grouped comment |

- Round 2 only re-evaluates round 1's findings and the new diff, so that a whole new batch of findings doesn't appear.
- A finding the builder disputed with a reason goes to the PR as pending, for you to decide.
- After the 2nd round, if a `blocker` remains, the PR opens as a draft and the description lists the pending findings at the top.

## Branches, PRs and comments

A large feature becomes an integration branch with medium-sized PRs. Only the integration branch opens a PR to the base.

```
dev
 └─ feat/checkout                        (integration)
     └─ feat/checkout-01-model           → PR to feat/checkout
         └─ feat/checkout-02-api         → PR to feat/checkout
             └─ feat/checkout-03-screen  → PR to feat/checkout
feat/checkout                            → final PR to dev

main
 └─ hotfix/pix-timeout                   → PR straight to main (+ back-merge to dev)
```

The slices are stacked: the flow builds all of them in sequence, without waiting for merges. Three rules keep this safe:

- If a slice ends with a pending blocker (draft PR), the flow stops there and stacks nothing on top.
- After you merge a slice into the integration branch, `/ship --restack <slug>` rebases the following slices and updates what each PR shows. It resolves simple conflicts and reruns the quality gate; on a logic conflict, it stops and calls you.
- PRs must be merged in order (01, 02, 03); each description says which slice it depends on.

Conventions:

- **Commits**: conventional commits with a scope, e.g. `feat(orders): add ownership check`. Review fixes use `fix(review): ...`, so the history is easy to read.
- **PR title**: the same pattern, e.g. `feat(checkout): 02 - payment API`.
- **PR description**: the slice goal, checked acceptance criteria, how to test, the reviewers that ran, and pending findings.
- **Comments**:
  - one summary comment per reviewer (`gh pr comment`);
  - the findings that have a line, as an inline review (`gh api .../pulls/<n>/reviews`, event `COMMENT`). GitHub doesn't let the author request changes on their own PR, so the event is always `COMMENT`.
- **Hotfix**: after the merge into `main`, `/ship --finalize` opens the back-merge PR to `dev` when `flow.json` asks for it.

## Reviewer checklists

Each checklist is a file in `checklists/`, anchored on a public standard:
- security: OWASP Top 10:2025 and ASVS 5.0;
- UX and UI: WCAG 2.2 AA and Nielsen's 10 heuristics;
- frontend performance: Core Web Vitals;
- code: clean code with hexagonal architecture.

Each project can extend them in `.claude/checklists/`. The full items are in the files themselves; the highlights are:

- **Security**: per-resource authorization and SSRF allowlists (A01); restrictive CORS, headers and least-privilege IAM (A02); justified dependencies and SHA-pinned CI actions (A03); argon2/bcrypt and no secrets in code (A04); parameterized queries (A05); rate limiting and idempotency (A06); strict JWT validation (A07); verified webhook signatures (A08); no personal data in logs (A09); fail closed with timeouts and DLQs (A10).
- **Code**: acceptance criteria covered by tests that would fail without the change; domain free of infrastructure; clear names and no `any`; typed errors; idempotent consumers; no N+1; reversible migrations; structured logs.
- **UX**: loading/success/error/empty states; error prevention and recovery; undo and cancel; consistency; keyboard and visible focus (2.4.7, 2.4.11); 24×24 targets (2.5.8); real labels and no re-entry (3.3.7, 3.3.8); clear copy.
- **UI**: design system tokens; 4.5:1 and 3:1 contrast (1.4.3, 1.4.11); 320 px without horizontal scroll (1.4.10); hierarchy and spacing; component states; Core Web Vitals at p75 (LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1); image and bundle weight.

## Implementation order

Five phases, each testable on its own in a test project before moving on.

1. **Skeleton and verification**: create the plugin repository and `plugin.json`, and install it locally. Check the current documentation for the plugin, skill and agent formats, the `model` parameter and `SendMessage`.
2. **`/flow-init`**: branch, command and stack detection; confirmation questions; writing `flow.json`. Test on a repo with only `main` and on another with `dev` and `main`.
3. **Spec writer and builder**: `/ship` through to the end of a single slice, with the quality gate and a commit, without reviewers or a PR.
4. **Reviewers**:
   - the four reviewer agents, the checklists, the JSON contract, glob routing, parallel execution and the loop of at most 2 rounds;
   - then the `browser-tester` with Playwright MCP, and E2E tests in the quality gate.
5. **PRs and slicing**: integration branch, one PR per slice, inline comments, drafts with pending findings, stacking with `--restack`, `--resume` and `--finalize`.

As the acceptance test for the whole plugin, run a small feature that touches both backend and frontend, and check that:
- the right reviewers were triggered;
- the loop stopped at the 2nd round;
- the PRs went to the right branches;
- the comments landed on the right lines.

The plugin is named `flow`, so the commands are `/flow:flow-init` and `/flow:ship`, and the agents are `flow:<name>`. The deterministic logic lives in `scripts/`, as dependency-free Node:
- detection;
- glob routing;
- review validation and consolidation;
- the inline comment payload;
- dev server lifecycle;
- PR text in both languages.

## Risks and open points

- [ ] **Stacking**: a change requested on an already-merged slice forces a rebase of the following ones. `--restack` covers the common case; logic conflicts stop the flow.
- [ ] **Cost**: four reviewers per round, up to two rounds per slice. Watch the usage on the first features.
- [ ] **UI reviewer without a browser**: it measures Core Web Vitals only by reading code. The `browser-tester` with Lighthouse covers this when `browser.prod` is configured.
- [ ] **False positives**: if a reviewer keeps getting the same kind of finding wrong, adjust the project checklist instead of adding rounds.
- [ ] **Changing docs**: the Claude Code documentation changes fast. Phase 1 exists to validate the formats before writing the rest.
